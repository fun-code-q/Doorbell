# Self-hosting QR Doorbell

This guide is for operators who want to run QR Doorbell on their own
infrastructure instead of Supabase's hosted plan — most commonly because
of data residency rules (where the database physically sits), cost
control at scale, or a regulatory obligation to keep audit logs in-house.

You don't need to do this to ship the product. The hosted Supabase plan
covers the entire feature set documented in [README.md](../README.md).

## Architectural fit

QR Doorbell is built on three Supabase primitives we genuinely use:

1. **PostgreSQL 16+** with `pgcrypto`, `uuid-ossp`, `pg_net`, `pg_cron`.
2. **PostgREST** (auto-generated REST API from the SQL schema).
3. **Supabase Edge Functions** (Deno runtime for `push-ring-notification`,
   `verify-ring`, `geocode-address`).

Plus a thin layer:
4. **Supabase Auth** (GoTrue) — JWT issuance.
5. **Supabase Realtime** — WebSocket → Postgres logical-replication
   broadcast.

The good news: all five components are open source. The bad news: they
don't ship as a single docker-compose by default in 2026 — Supabase's
self-host story is multiple repos that need to be glued together.

## Two viable paths

### Path A — Supabase OSS via the official self-host repo

```
git clone https://github.com/supabase/supabase
cd supabase/docker
cp .env.example .env
# Edit .env: set POSTGRES_PASSWORD, JWT_SECRET, ANON_KEY, SERVICE_ROLE_KEY,
# SITE_URL, etc. (See supabase.com/docs/guides/self-hosting/docker.)
docker compose up -d
```

This brings up Postgres + GoTrue + PostgREST + Realtime + Studio + Kong
(API gateway) + the rest. You then apply our SQL migrations:

```
cd /path/to/qr-doorbell
supabase link --project-ref local      # actually uses the SUPABASE_URL above
supabase db push                       # applies supabase/migrations/
```

Pros: same Studio UI, identical API surface, all features just work.
Cons: it's a meaty docker-compose (~12 containers); needs a beefy host.

### Path B — Minimal "just the schema" deployment

If you don't want the full Supabase suite, you can run:

- **Postgres 16+** (managed: AWS RDS / GCP Cloud SQL / Hetzner)
- **PostgREST** as a single binary (`postgrest <config>` ~ 20 MB)
- **PgBouncer** for connection pooling
- **A custom JWT issuer** (or Auth0 / Keycloak / Authelia) issuing the
  same shape of JWT as Supabase Auth: `role` claim set to `anon` or
  `authenticated`, plus `sub` = user id

You then run our migrations as plain `psql` scripts:

```
psql "$DATABASE_URL" -f supabase/migrations/20260518000000_extensions_and_core_tables.sql
# ... and so on for each migration file in order.
```

**Edge Functions** can run anywhere that hosts a Deno service — Fly.io,
Cloud Run, even a Raspberry Pi. The webhook secrets and FCM service
account live as environment variables.

**Realtime** is the trickiest piece. The simplest substitute: a
PostgreSQL `LISTEN`/`NOTIFY` channel + a tiny WebSocket gateway. The
[`supabase/realtime`](https://github.com/supabase/realtime) Elixir
service works standalone if you want full feature parity.

Pros: minimal moving parts; small attack surface.
Cons: you give up Supabase Studio (use pgAdmin or pgcli instead); you
take on JWT issuance and Realtime broadcast yourself.

## What the QRVault Android app needs

The app only knows three things about the backend:

1. `SUPABASE_URL` — set in `local.properties` or GitHub Actions secrets.
2. `SUPABASE_KEY` (the anon key) — same.
3. `GUEST_BASE_URL` — where the guest web app lives. Often the same
   host as the API, or its own static CDN.

Point these at your self-hosted endpoint and rebuild. Nothing else in
the codebase assumes Supabase Cloud specifically.

## What the guest web app needs

`public/runtime-config.js` (generated by `.github/workflows/deploy.yml`)
carries `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `VERIFY_RING_URL`. Point
those at your self-hosted endpoints. The browser doesn't care that the
hostname isn't supabase.co.

## Migration from hosted to self-hosted

1. Export schema + data from hosted Supabase:
   `supabase db dump --data-only > data.sql`
   `supabase db dump --schema-only > schema.sql`
2. Apply schema to new instance via `supabase db push`.
3. Load data via `psql "$NEW_URL" -f data.sql`.
4. Re-mint FCM service account JSON (one-time, per `USER_ACTIONS.md`).
5. Re-issue the anon JWT on the new auth service so the existing token
   format stays compatible (or rotate clients to take new tokens).
6. Cut over DNS or update `SUPABASE_URL` in your build configs.

## What does NOT carry over automatically

- **Push subscriptions**: FCM tokens are device-issued; existing tokens
  keep working as long as the Firebase project is the same. If you're
  also moving Firebase projects, every device must re-register.
- **Encrypted-key backups**: the wrap is local-keystore based, so the
  per-device backups still work — they don't depend on the server URL.
- **Audit log**: copies over as data.
- **Realtime subscriptions**: clients reconnect on next foreground.

## When to bother

Honestly, almost never for a single-tenant doorbell deployment. The
operational overhead of running Postgres + Edge runtimes + Auth + WS
yourself dwarfs the cost of Supabase's hosted Pro plan unless you're
operating at thousands-of-properties scale.

The reason this doc exists is so the codebase isn't *locked* to Supabase
— operators with policy reasons (German government deployments, EU
agencies that can't use US-controlled clouds) have a clear escape hatch.
